# HyperFurion VK 3

Proposal, written against 2.4.0. This is a design, not a schedule, and
not a commitment that every paragraph ships. The current release is
declared in `pyproject.toml`. The seven rungs in `ROADMAP.md` stay the
direction. Version 3 picks a spine through them.

The promise: the sentence you are still saying stays underlined in the
app you already have open, and only the words that have settled become
ordinary text.

## What 2.4 already is

2.4 is a system keyboard. The mic opens when you press. Speech becomes
real keystrokes in whatever app is focused, including a terminal. With
the default speech stream, words appear while you talk and repair
themselves in place. In a terminal the keyboard recognizes, Enter is
never pressed. Kai answers only after you summon it, and stays off when
a question would leave the machine until you turn it on. A word you
spell or correct is offered to your dictionary and applied only if you
accept it.

The repairs are done by deleting and retyping. `FlowEngine.desired_text()`
is the frozen text plus the still-molten preview, and `InjectionWorker`
backspaces the tail until the screen matches. That is correct for a
virtual keyboard. It is also why a click in the middle of a sentence
lands the next repair in the wrong place, and why "scratch that" gives
up on emoji: backspace across complex characters is not reliable. On
Wayland the daemon often cannot see the focused app at all. GPU
terminals expose no accessibility tree, and GNOME often refuses the
look. When focus is unknown, spoken line breaks become spaces and Enter
stays suppressed, which is safe and feels like the keyboard is guessing.

`PreeditMapper` in `voice_keyboard/imethod.py` already turns that same
frozen-plus-molten state into commit, delete, and preedit operations.
Nothing in the daemon calls it. `SPOKEN-INPUT-PROTOCOL.md` keeps the
host unwired on purpose: registering an input method touches how the
whole desktop types, so it has to be a choice, including on upgrade.

## The spine

Version 3 adds one opt-in process that speaks ibus. The flow engine's
stability window is the only commit. Molten text is the underline.
Frozen text is the only text that enters the app. Whenever that process
has no client attached, typing stays on uinput, and the session is a
2.4 session.

The other places to spend a version lose for a specific reason.

Extending the accessibility probe spends it on the sensor Wayland is
failing to provide. Code compilation in `voice_keyboard/flow/code.py`
and pending rewrites still have to land through the same backspace
storm until the sink changes. Always-on dictation, and a
speech-to-speech takeover of the keyboard, both act before a commit
rule exists. A freedesktop submission writes the protocol down before
one host has applied the mapper that is already tested.

## What you feel

### In a browser or a document

You tap Ctrl+Alt+V in the window you already focused.

Words appear at the cursor in the app's own type. One underline sits
under the part you are still saying. As a word settles, the underline
lifts off it from the left and it becomes normal text. A listening dot
by the cursor is the only chrome. It does not repeat the sentence and
it does not take focus.

You hear one soft high tick when the microphone opens and one low tick
when it closes.

While a stretch is underlined, "scratch that" clears that stretch,
emoji included, because those characters are not in the page yet. A
click, or any key you press yourself, drops the underlined words and
leaves the settled ones. After the underline has lifted, "scratch that"
removes the last phrase you said, as that phrase. If the cursor has
moved and the place is no longer sure, the phrase stays on the page and
the small line offers it so you can say "type it" where you are now.
The page's own undo still works on settled text.

A spoken "new line" in a chat is Shift+Enter, after the underlined
words have settled. Your own Enter still means what that page means. If
underlined words are up when you press it, they settle first and then
the Enter goes through.

### In a terminal

A command is a draft until you run it.

When the terminal can hold an underline, the draft is that underline,
and a commit never includes Return. When it cannot — Ghostty, kitty, and
anything else that never attaches an input client — the same draft
lives in the small strip beside the prompt. When it settles, or when
you say "keep it," the characters type onto the prompt once, forward,
with no Return after them. You press Enter yourself.

"New line" stays one line. Nothing executes. "Scratch that" before the
draft lands means the shell never had it. After it lands it is ordinary
prompt text.

### Kai

Kai is off until you turn it on whenever a question would leave the
machine. You hold Right Ctrl. The page you were typing in does not gain
words. A command Kai drafts uses the same draft as a command you
dictate: Kai speaks the line, and the line types onto the prompt only
when you say "keep it." A tap cuts the answer off. The first time you
hold Right Ctrl while Kai is off, you hear one sentence: Kai is off,
and where a question would go if you turn it on. That sentence does not
repeat all afternoon.

Kai's notes stay on this computer until you turn memory off.

Spoken answers may later use the public Grok realtime voice. Dictation
stays the transcribe stream, because that stream is what the engine can
freeze word by word. The two sockets do different jobs. The Grok Voice
plugin in Cursor is a skill for building voice into other apps. It is
not part of this keyboard, and version 3 does not grow a waveform or a
composer.

## The rule

Underlined isn't finished. Finished isn't run. Spoken only happens
because you asked.

Your own settled words are typed as you go. The period a pause invented
stays underlined until the words after it decide, which the engine
already does. A snippet you named is typed because you asked for those
exact characters. A rewrite stays underlined until you say "keep it" or
"scratch that." A command becomes text on the prompt and waits for your
Enter. Kai may speak an answer you asked for, the one line of a command
it drafted, and the one sentence about where questions go. Kai does not
read the page aloud and does not announce words it hopes you will
remember.

## Where the two passes disagreed

The interaction pass wanted a hard gate: if the desktop cannot name the
focused window, type nothing until you say "type it." The engineering
pass wanted unknown focus to keep today's behavior, which types with
Enter suppressed.

Both are right about a different risk. Refusing to type whenever focus
is unknown would silence the keyboard on the Wayland sessions that need
it most, for every user who has not turned the underline on. Typing a
command into a window we cannot name is how a draft becomes a surprise
at the wrong prompt.

Version 3 splits them.

Ordinary dictation, with the input method off or with no client
attached, still types. Enter stays suppressed and a spoken line break
becomes a space when the window cannot be named, as in 2.4. The overlay
says we cannot see the window, and the unfinished tail is drawn in the
small line because the app cannot underline it.

A command is different. Intent, and Kai's terminal route, stay in the
strip until you say "keep it" whenever the focused window cannot be
named. A command is never the thing we guess a destination for.

"Type it" exists for one case: settled words whose place was lost
because you clicked away. It does not become the way ordinary dictation
lands.

## How it is built

### Two processes

The daemon keeps the microphone, speech-to-text, the flow engine, the
registers, and Kai. A new process under `voice_keyboard/imhost/` is the
only thing that speaks ibus. It gets its own systemd user unit,
`voice-keyboard-im.service`, installed disabled. ibus needs the system
`gi` bindings, and the virtualenv does not have them. The focus probe
already runs under `/usr/bin/python3` for that reason. A host crash
must not take the microphone down with it.

### A stream, not the command socket

The daemon's command socket accepts one command, writes one JSON reply,
and closes. Preedit is a stream. A second socket, mode 600, takes one
long-lived connection. Messages are newline-delimited JSON.

The host sends `hello`, `attach` (with the field's purpose and hints),
`detach`, `ack` (a generation), and `reset`. The daemon sends `ops`,
`keys`, and `clear`. The host reads every message.

### The switch

`[im] enabled` defaults to false. A missing key means off. An upgrade
does not write it into an existing config, does not start the unit, and
does not change the user's input sources. Turning it on is an edit plus
the desktop's input-source picker. `voice-keyboard doctor` reports
whether the host is registered, whether a client is attached, and that
keystrokes still work when ibus is absent.

If the flag is on but the host is down, ibus is down, or no text client
is attached when recording starts, the session is a 2.4 session. The
injection worker runs. The overlay says it is typing as keys. The
hotkey is never blocked. One log line per session, not per tick.

### The molten tail is not typed twice

`desired_text()` is the right string for uinput, because the worker
backspaces the preview. It is the wrong string to commit: committing it
types the unfinished words, and the underline draws them again.

The engine gains `committed_text()` and `molten_text()`. One sink per
session. An attached client means no injection worker for that session.
The sink calls `PreeditMapper.update(committed, molten)` and pushes the
operations. The host applies them in order: commit the frozen delta,
then replace the underline with whatever is still molten. It does not
also commit the previous underline.

The mapper moves forward only after the host acks that generation.
Until the ack, the ticker keeps the latest pair, the same way the
worker drops a stale burst. If the ack never comes, the session
freezes what is already on screen. It does not backspace, and it does
not switch this utterance over to uinput. Switching mid-phrase is how
text gets typed twice. The next recording may fall back cleanly.

When the session ends, `finalize()` clears the underline and commits
nothing. A toolkit that then commits a stale underline is ignored.

Navigation stays on this path. The engine already parks a barrier until
the keys go out. The sink flushes commits, clears the underline,
forwards the chord, then completes the action. A forwarded chord that
would be Enter is refused, and dictation resumes so the words are not
dropped.

### Enter still cannot fire

The filter keys off the newline choice, not off the register's terminal
flag. The python register is not a terminal register. Pointed at a
terminal app, the compiler can emit a newline. Today's injector strips
that newline because Enter is suppressed. A raw commit of the compiler
string would press Return by another name.

`guard_commit` lives next to the injector's line-break strip. The sink
runs it on every commit and every preedit when the newline choice is
none. Return, keypad Enter, Ctrl+M, and Ctrl+J are dropped on the
forwarded-key path in that same case. The human key command on the
existing socket stays the exception it already is.

A chat line break is a forwarded Shift+Enter after the line has frozen.
It is not a newline character inside the commit. A committed newline is
how those apps send the message.

Intent and Kai's command route stay draft text. With a client attached,
that is one commit of the stripped command and an empty underline,
still under the Enter refusal. The terminal inserts the text. It does
not run it. If a client is ever observed to submit on commit, the host
refuses commits while the purpose is terminal, and that session falls
back to uinput with Enter suppressed. The failure mode is draft
keystrokes.

The shell compiler never grows a Return. A python indent, in an editor
whose newline choice allows a real line break, is one forwarded Tab at
the moment the line freezes. While the line is underlined, the tape
stays text, so a revision repairs the underline and does not have to
undo a key.

### The field tells us what it is

Once a client is attached, the field's purpose and hints are the field.
A terminal purpose selects the terminal register and newline none. A
password, a PIN, or a hidden hint selects verbatim: no hotword bias, no
history, no rewrite. A URL purpose selects verbatim. A field with no
multiline hint is one line, so newline is none. The caret for the
overlay comes from the input method's cursor rectangle. The
accessibility probe does not start for that session.

There is no purpose value for a code buffer. Version 3 does not invent
one. The python, shell, and javascript registers stay a choice in
`[registers].map` or a spoken register.

A purpose wins, and a late probe cannot override it. That is what
closes the hole for GTK and Qt fields, including a terminal widget that
already sets the terminal purpose. On GNOME those are often the fields
the accessibility tree cannot see, so Kai stops treating a known text
field as "maybe a terminal."

No client attached, and the host is up: skip the accessibility probe on
the hot path. On a wlroots compositor, a socket the user already has
may answer an app name quickly, and that name goes through the register
map we have. If it does not answer, the field is unknown.

The input method is off: today's probe, unchanged.

Unknown still means no Enter.

## Three mechanisms inside the spine

The stability window becomes the commit rule by construction, and a
test locks it. Scripted transcripts and a fake clock drive the engine.
`committed_text()` and `molten_text()` go through `PreeditMapper`. A
token younger than the stability window must never appear inside a
commit. The host does not grow a second timer. `max_molten_chars` and
the adaptive revision depth stay in the engine.

The underline carries a provisional mark as an attribute on the preedit
operation, drawn as one underline. No invisible character that could
leak into a commit if a toolkit misbehaves. Committed text is the app's
to spellcheck, because the unfinished words never entered the buffer.
The protocol draft's provisional style waits until this attribute has
been wrong in a real client.

Kai's spoken answers can move to the public realtime voice without
touching dictation. `voice_keyboard/assistant/realtime.py` is the only
place that changes, behind a config value that keeps today's agent URL
as the default. The converse turn already has the audio. The terminal
classifier stays in front: a command still goes through the draft path
and the Enter refusal. A spoken answer never reaches the injector.
`can_act` stays off.

## First run

You already have a window focused. Setup asks one thing: where speech
should be heard, a key or the address of a speech server on this
machine. Then it tells you to click back into that window and press
Ctrl+Alt+V.

On a desktop that can underline in the focused app, it asks one yes to
show unfinished words underlined there, and it leaves the keyboard you
already use in place. You get a word in that window before any logout.

If that desktop cannot underline, it asks permission to type, tells you
that you will log out and back in once, and uses the small line until
then.

This shorter path is for a new config only. `voice-keyboard setup`
keeps the full walk for someone who asks. The first time you say "make
that formal," that is when it asks for a language model. The first time
you summon Kai and a question would leave the machine, that is when it
asks you to turn Kai on.

Setup does not ask about a wake word, history, caret commands, a
hotkey, or a menu of speech services on that first run. The language
follows the session, said in one line.

## Left out

Always-on dictation waits. The underline makes an unfinished tail able
to evaporate, which is the containment ambient mode needs, and it
matters only after that underline is what people actually see. The
hotkey stays the hard mute. A wake word, if you later turn it on, only
summons Kai.

The freedesktop submission waits. `SPOKEN-INPUT-PROTOCOL.md` already
says that mailing list is a separate act. One ibus host will show
whether commit and preedit are enough. A provisional style and a code
purpose stay local until a second implementation exists.

Local fine-tuning waits. The correction loop that exists is the
personal dictionary and `voice-keyboard learned`. Nothing applies until
you accept an entry.

Flatpak waits, for the reason `packaging/DISTRIBUTION.md` already
gives. The job is to type into other apps. An input-method host also
has to sit on the session bus and be chosen as an input source. The
curl installer and the AUR package stay the channels.

A Wayland input-method client for Sway and Hyprland waits. Version 3
ships the ibus host only. GNOME will not load anything else, and GNOME
is where the focus probe fails. Plasma often runs fcitx5. Sway and
Hyprland will not see an ibus engine. Those sessions keep uinput, and
that is the design, not a gap we paper over. A second process on the
same socket comes after ibus has survived a release.

There is no second app, no caption that repeats words already
underlined in the field, and no dialog asking you to confirm a command.
The confirmation for a command is the Enter you were already going to
press.

## What does not move

Enter cannot be emitted by any path while the newline choice is none,
including a newline hidden in a paste.

A command is typed and left. The model does not get a way around that.
The refusal stays in the sink, not in a prompt.

Frozen text shrinks only because you scratched it, corrected it, or
undid it.

Kai under its default setting stays off when anything it does would
leave the machine.

A password field is never biased, never remembered, and never rewritten.

A personal word changes nothing until you accept it.

The microphone stays closed until you press, unless you have opted into
the wake word.

The input method is never turned on by an upgrade.

## Risks

ibus is the host that fixes GNOME. Sessions that do not run ibus have
to keep feeling like 2.4. A fallback that is worse than today's typing
is a failed release even if the underline is beautiful on one desktop.

The input-source picker is a gesture you make. Doctor prints the one
command. The daemon does not touch input-source settings on upgrade.
The `input` group stays required, because a terminal that never
attaches still needs the virtual keyboard.

The new unit is not tied to the daemon unit. Restarting the daemon
leaves a disabled host stopped. A host you enabled reconnects on its
own when the daemon comes back.

Continuous integration does not need a compositor. The engine-to-mapper
test is pure. A fake host applies the operations into a string and
checks that the string is the frozen text plus the underline, and that
a command ending in a newline becomes the command with no Return when
the newline choice is none. The existing terminal Enter tests stay the
uinput contract. The `gi` process is skipped unless an ibus address is
set, the same way the live macOS tests already skip. Doctor is the
check on a real session.

Linux CI today does not prove that uinput reaches a real app. Version 3
does not pretend a new unit test replaces that. The pure tests lock the
commit rule. A recorded GNOME session is the acceptance test before
anyone is asked to turn the underline on. The flag defaults to false
for the whole version.

One fact has to be checked on GNOME 45 through 50 before setup offers
the underline: whether the terminal widget actually reports a terminal
purpose for the focused tab. If it does not, a terminal looks like an
ordinary multiline field, and a committed newline could submit. Until
that is confirmed, a terminal we cannot prove stays on uinput with
Enter suppressed.

## How the work is cut

Each slice is its own branch and its own pull request, and each one
leaves the keyboard behaving as 2.4 while the flag is off.

1. The two engine accessors, and the test that a young token never
   appears in a commit. No host. No behavior change.
2. `guard_commit` on the uinput side, so the newline rule exists before
   a second sink can violate it.
3. The stream socket and a fake host in the tests.
4. The ibus process, the systemd unit installed disabled, the doctor
   lines, and `[im] enabled` defaulting to false.
5. The shorter first run, only when the config is new.
6. The optional realtime voice for Kai's spoken answers, after the
   underline path is in review. It is not on the critical path.

The underline host does not share a branch with the Kai voice change.
They fail differently, and only one of them touches how the desktop
types.
